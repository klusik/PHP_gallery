## Executive technical conclusion and acceptance gate

The original hosted baseline establishes real cold thumbnail, disk/RAM reuse, tree-v1, legacy overflow, Xvfb native Tk, PHP timing, faults and FIFO Watcher/upload measurements. It **does not** justify A1 completion by itself: the original mutation test incorrectly reported PASS even when it returned stale disk bytes after an actual scanner mutation.

A1.4 repairs that concrete correctness gap. The production server now proves the same small fallback-original bytes served by its thumbnail endpoint, without exceeding the existing 128 KiB per-descriptor SHA-256 budget. The WinApp preserves live catalogue epochs, refuses superseded or deleted public thumbnail descriptors, requires real 200/304 revalidation for unproven new-page originals, scopes decoded RAM identity to current catalogue epochs, and replaces previously displayed unproven tiles. An actual disposable source replacement, oversized fallback, addition and deletion are asserted against independently fetched authorized response bodies and Pillow-decoded pixels.

**Immutable qualification rule:** A1 may be marked PASS only if final BASIC and the full A1 hosted workflow both succeed on the exact commit containing this report, their raw artifacts satisfy the assertions below, and the issue checkbox is subsequently verified from GitHub. In particular, the prior mutation JSON is a false positive, not a valid A1 T3 PASS. This report does not represent unexecuted future workflow results as measured observations. The authoritative final run IDs, statuses and exact source SHA belong in the signed GitHub Actions records and final issue #362 verification comment.

## T6 real complete legacy pagination

The real tree-v1 endpoint rejected the 10,001-row overflow; the unchanged legacy endpoint returned **201** valid pages with **50** entries per full page and exactly **10,001** unique total galleries. The client respected a **5,000 ms** delay after the first **10** pages. Total end-to-end elapsed **968,480.441 ms**; actual accumulated pacing wait **955,026.197 ms**, approximately **98.61%** of the observed duration. The test observed **0 HTTP 429** without modifying the server rate limiter. This evidence does not prove the physical Tk scheduler; that is covered by independent Windows tests.

## T3 exact-body, deletion and cancellation acceptance

A1.4 must report server SHA-256 before and after two production-scanner mutations, source SHA-256 of the client's *actual bytes*, ETag presence for the small original fallback, absent ETag for the deliberately oversized original, and correct conditional revalidation on a new metadata page. It must compare actual Pillow-decoded RAM pixels to an independently fetched authorized image, preserve an unrelated proven disk entry, download a new photo once, and refuse a deleted old descriptor before cache/network publication. A second `LinkingSession` must not inherit the previous metadata epoch.

A strong ETag can prove matching bytes cheaply for small fallbacks and already materialized thumbnails; the bounded metadata digest must **never** hash an arbitrary large original. An unknown validator is not proof that a recently stored disk body still matches a newly authorized page. A correct 304 permits reuse of an identical, SHA-verified retained body only after the actual authorized response passed policy checks. No cancelled operation may reintroduce a stale GUI generation or bypass the session gate.

## T7 retry, backoff, timeout and release

The disposable HTTP router directly injects 429, JSON 502/503, HTML 502/503, truncated payloads, and a slow response for active-read cancellation. Typed client errors must preserve the HTTP status, reject the response body, and create no cache entry. The existing Windows-native suites independently exercise Retry-After parsing, DNS/connect failures, connect/read timeouts, cancellable retry/backoff, foreground priority, session teardown and refusal to automatically replay an ambiguous multipart upload. These tests do **not** establish the root cause of real WEDOS 502/503 responses; external WEDOS metrics remain UNKNOWN.

## T8 actual FIFO and multipart upload

The observed completion order was **preload_first**, **watcher_inventory**, **catalogue_refresh**, **multipart_upload**, **preload_second**. Watcher end-to-end latency was **131.110 ms**; multipart upload **648.716 ms**; exactly one file was uploaded and later found once in the authorized photo catalogue. There was no observed starvation. The PHP CLI server and client FIFO serialize requests, so these are not independent production worker concurrency measurements.

## Quantified bottleneck ranking and decision

1. **Policy pacing at 10,001 legacy rows:** 955.026 seconds of 968.480 seconds total, 98.61%. Not a network or SQL bottleneck; do not change the rate limiter or bypass its budget for A1.
2. **Per-thumbnail cold HTTP/authorization/TTFB:** 120 round trips, 10.967 seconds total, p50 50.299 ms TTFB and 57.565 ms client elapsed. A batch protocol can reduce request count, repeated HTTP framing and authorization/connection handling, but cannot remove transfer bytes or actual image decode.
3. **GUI first-visible path:** 1.913 seconds for 20 actual Tk tiles; first Tk `PhotoImage` 246.590 ms. Includes serialized transport and event scheduling. Actual image attachment aggregates only 11.782 ms, so optimizing Tk attachment alone is unlikely to eliminate cold transport latency.
4. **Server tree-v1 model/SQL and reconciliation:** at 10,000 rows, median service 13.533 ms and model-plus-SQL 7.628 ms, five SELECT. Worth monitoring in provider-like load, but present staging evidence alone does not justify an immediate server-side tree cache.
5. **Revision serialization/hash:** at 10,000 full rows, median revision JSON 1.103 ms and SHA-256 0.349 ms. The revision function still reads/model-processes rows on unchanged responses.
6. **Client queueing and upload contention:** in the FIFO sample, the second preload waited 638.298 ms for the gate, while one real upload finished in 648.716 ms. Fairness is demonstrated, not an absence of queue latency.
7. **Local disk/RAM cache and Pillow:** disk p50 0.165 ms, RAM p50 0.0088 ms and decoded cold p50 0.935 ms per image. These are orders of magnitude below cold HTTP elapsed in this fixture.
8. **Filesystem, exact SQL execution, real network versus loopback, and WEDOS worker occupancy:** not isolated by an independent compatible instrumented sample. Rank **UNKNOWN**, never derive by subtracting unrelated clocks.

**A2 / B1:** GO for benchmarking a bounded thumbnail batching protocol **only after** the final A1 exact-SHA tests and checkbox confirm the cache/GUI/authorization corrections. Batching can amortize per-image request overhead but retains server image read/transform, bytes, security boundaries, client Pillow decode and visible-tile scheduling. **C1:** GO for bounded provider-relevant timing measurements with correct instrumentation. **C2:** NO-GO for implementing a speculative server tree cache at this stage; first validate repeated tree-v1 cost and worker occupancy in relevant hosting conditions. No batch API, C2 cache or public diagnostics are implemented here.
