# Develop integration and BASIC release delta contract

The maintainer's 2026-10-12 clarification replaces the earlier full-feature,
post-push-develop and per-child release-reuse proposal. The approved entry point
is **Integrate into develop** in GitHub Actions. The earlier workflow/input
approval question is superseded by this explicitly requested execution policy.
These source changes are not installation on protected main; hosted fixtures do
not demonstrate an executed protected integration or release.

## Required cadence

| Stage | Execution and immutable identity |
| --- | --- |
| Feature push or squash | BASIC: PHP/JavaScript syntax and named-declaration documentation only. No preparation or functional matrix. |
| Select squashed feature | S must have exactly one parent, current develop P. Refuse unsquashed, merged or stale work before generation. |
| Prepare integration | Read-only generation produces only runtime modules, production inventory and core manifest. API-only publisher creates direct child A of S if needed; otherwise A=S. |
| Integrate into develop | Execute the complete existing FULL matrix once on exact A with base P. After success and renewed leases, publish exact-A checks and perform non-force FF. |
| Release from A | Authenticate retained main-owned integration before generating notes, four locked manuals/PDFs, version/metadata, inventory and manifest into B. |
| Qualify B | BASIC `--changed` at immutable A and complete release-owned A..B evidence. No browser, DB, PHP regression, Node fixture or WinApp regression replay. |
| Approve and complete | Existing human exact-B PR approval, protected M with parents [Pmain,B] and tree(B), immutable tag and unpublished draft remain. Publication is manual. |
| Post-release develop FF | Retain B qualification without another matrix. Parallel develop work still refuses reconciliation. |

`scripts/audit.php` remains the sole test orchestrator. BASIC has exactly
`php-lint`, `js-lint`, `source-documentation-changed`; `--changed` uses
`php-lint-changed`, `js-lint-changed`, `source-documentation-changed` and requires
a readable literal ancestor SHA. BASIC needs PHP, Node and Git; it does not
discover Python, GD, databases or Chromium. `quick` remains a separate diagnostic.

FULL retains preflight, two PHP compatibility/source profiles, three disposable
DB/HTTP/security/race profiles, required Chromium, three OS packages and the native
aggregate: eleven owners. The release-only audit is expected skipped in FULL.
No required capability is removed. CI infrastructure can be explicitly qualified
through `maintenance_full` dispatch on the candidate workflow; this deliberate
hosted maintenance operation never automatically runs on ordinary feature pushes
and never writes develop or main. It retains a successful BASIC source job before
preparation, so the newest explicit FULL attempt also has independently verifiable
BASIC evidence for S; a failed or unfinished newest attempt still blocks selection.

## Authority and evidence

The manual integration workflow runs from protected main source W, distinct from
S/A. Privileged jobs check out W only; candidate generation and FULL jobs have
read-only permissions and no persisted write credential. Generated bytes cross
the boundary as bounded, provider-digest-verified data. Only
`app/runtime/modules.php`, `app/production-files.json` and `app/core-manifest.json`
may appear in generated A's direct child of S. Publishers recheck source/P, use
non-force writes and read the resulting ref. They do not fabricate an atomic
expected-old guarantee for GitHub's ref API.

BASIC S uses `Basic source qualification`, binding `basic:<run>:<attempt>:<S>`
from `candidate-preparation.yml`; it never publishes the FULL context.
The native run suite and the REST-created custom check suite are authenticated
separately: GitHub can group a new custom check into an earlier suite for the same
commit/App. Exact native run/attempt/job evidence remains the execution authority;
suite grouping alone must not reject a valid newer run or accept a foreign one.
The BASIC workflow and its complete executable audit/documentation input closure
must be inherited byte-for-byte from protected P. A feature cannot qualify its
own changed evaluator. CI harness updates use the explicit hosted maintenance and
maintainer review process; the first installation retains the full bootstrap.
Integration requires actual successful BASIC and all eleven native FULL owners
before creating `Develop integration qualification` and `Complete required CI
matrix` bound to `integration:<run>:<attempt>:<A>`. The final publisher is still
in progress during FF; subsequent release consumers require its enclosing run
completed-success, retained W in main history, exact run/attempt/check IDs,
native owner IDs and A tree. The moving develop ref is not the release identity.

Lifecycle schema 3 / coverage schema 1 is explicit. Schema 1/2 retain historical
FULL validation. New records contain separate authenticated integration/delta
identities. Schema 3 authenticates native strict owners and filters only explicitly
validated skipped bootstrap rows before counting those owners; foreign or unknown
strict jobs are refused. Provider artifact IDs/digests live outside payloads, avoiding archive
self-reference. Consumers authenticate complete raw ZIP SHA-256, entry sizes/CRC,
exact file names and original central BASIC report digest. Expired, truncated,
duplicate, stale or red evidence blocks qualification; older green evidence
cannot hide a newer retained red identity.

`source_base` remains the previous stable release candidate for origin, notes,
assets and completion. `delta.base_sha` is A and does not redefine that field.
Exact source S, prepared A, workflow W, release B, trees, modes and old/new blobs
remain separate identities.

## Release delta ownership

A..B permits only the current version's newly added origin/predecessor records,
existing release Markdown/notes/metadata owners, four manual `.tex`/`.pdf` pairs,
production inventory and core manifest. Regular modes remain unchanged.
Functional source, tests, helpers/CI, migrations, runtime modules, deletions and
renames are refused and return to a newly squashed candidate for FULL integration.

The sole executable projection is one canonical `CMS_VERSION` literal in
`app/bootstrap.php`, changed to the requested version with every other byte
identical. This is the maintainer's explicit BASIC-only preparation policy, not
a claim that all version consumers are behaviorally independent. The former
proposal to replay semantic version-consumer tests is superseded.

All four locked manual builds, generated freshness, release consistency, asset
package/hash checks and exact-head leases remain generation/completion owners.
Unchanged manual sources need not be artificially modified. `winapp_changed`
is false for A..B; separate `installer_required` records prior-release-to-A impact
and retains the current conditional installer artifact build. Artifact production
does not rerun functional or WinApp regression suites.

## Qualification and installation

Registered inert fixtures cover BASIC bases, squash/ancestry, main workflow
authority, generated-only publishing, leases, native/check binding, corrupt ZIPs,
provider mismatch, newest red evidence, release path/mode refusals, version-only
projection and legacy schema compatibility. Only hosted execution on the exact
prepared SHA qualifies the source change. Installed Windows/UAC/restart/live
SimConnect and live installation/manual acceptance remain explicit gaps.

The reviewed integration workflow must be installed through the maintainer's
protected process before its button is available. A branch-local green check
does not authorize an agent to write main/develop, create a release branch, tag,
upload assets or publish. Existing server controls and #101 approval remain.

The first installation retains the legacy full release lifecycle as
`release-bootstrap.yml`. The release selector reads the integration workflow at
one immutable main SHA; only an explicit missing-file 404 selects that bootstrap.
Other API failures block. Once the workflow is installed, missing or red
integration evidence cannot fall back to the legacy matrix. This one installation
exception installs the requested cadence without requiring the new button to
exist before the release that introduces it.
