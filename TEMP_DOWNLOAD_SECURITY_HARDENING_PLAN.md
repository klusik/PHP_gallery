# TEMP PLAN: Public Gallery Download Security and Resource-Amplification Hardening

> **Temporary implementation source document.**
>
> Keep this file in the repository root while the staged implementation is in progress.
> Remove it only after every stage in this document has been implemented, tested, deployed,
> and the final post-deployment verification has been completed.
>
> This document is intentionally **not** a patch note and must not be copied into
> `PATCH_NOTES.md` during implementation unless a later release task explicitly asks for that.

## 1. Purpose

The public gallery download feature is intentionally open to anonymous visitors. The goal of
this hardening work is therefore **not** to identify humans, force authentication, introduce
CAPTCHAs, require email verification, or throttle legitimate download bandwidth.

The goal is to make public download requests safe even when they are generated by crawlers,
scrapers, scanners, malformed clients, or deliberately abusive automation.

The central security invariant is:

> **An unauthenticated public request must not be able to amplify a cheap HTTP request into
> unbounded expensive PHP, filesystem, database, ZIP, CPU, memory, or temporary-storage work.**

The current progressive browser downloader is already architecturally preferable because the
browser receives a manifest, fetches authorized source files, and assembles the ZIP locally.
The remaining hardening work should reinforce that design and gradually demote the old
server-side ZIP route from a crawlable fallback into a deliberately initiated, bounded legacy
compatibility path.

This is a **fundamental resource-control redesign**, not an anti-bot blacklist.

## 2. Current implementation observed before starting

The authoritative codebase used to write this plan currently contains these public routes:

- `download_gallery`
- `download_gallery_manifest`
- `download_gallery_file`
- `download_smart_gallery`
- `download_smart_gallery_manifest`
- `download_smart_gallery_file`

Relevant implementation areas currently include:

- `app/controllers/downloads.php`
- `app/services/downloads.php`
- `app/bootstrap/dispatch.php`
- `app/bootstrap/routing.php`
- `app/services/seo_request_guard.php`
- `app/controllers/public_gallery_page.php`
- `app/controllers/smart_galleries.php`
- `public/assets/gallery-modules/gallery-download.js`

The physical-gallery public action currently renders an anchor whose `href` points to the
legacy `download_gallery` route while JavaScript intercepts the click and uses
`download_gallery_manifest` for the progressive browser ZIP workflow.

The Smart Gallery action follows the same general pattern.

The legacy route already has useful upper bounds:

- `GALLERY_DOWNLOAD_LEGACY_MAX_FILES = 1000`
- `GALLERY_DOWNLOAD_LEGACY_MAX_SOURCE_BYTES = 268435456`

The progressive manifest also has hard upper bounds on the number of files/galleries.

These protections must remain in place unless a later stage replaces them with stronger,
explicitly tested limits.

### Observed incident motivating this work

Automated traffic reached `download_gallery` across a large number of gallery IDs and caused
repeated `gallery.download_legacy_failed` events. This is compatible with a crawler following
public anchor URLs without running the JavaScript interception logic.

The incident does **not** by itself prove compromise. It demonstrates that a public crawler can
enter the legacy server-side ZIP path simply by following discoverable GET links. That is the
resource-amplification surface this plan removes.

## 3. Non-negotiable product requirements

All stages must preserve the following requirements.

### 3.1 Public anonymous downloads remain available

Do not require:

- CAPTCHA
- login/account creation
- email confirmation
- email-delivered codes
- phone verification
- external identity providers
- proof-of-work challenges
- JavaScript puzzles intended to distinguish humans from bots

### 3.2 Do not throttle legitimate transfer speed

Do not introduce per-user or global bandwidth limits such as:

- fixed MB/s caps
- artificial sleeps during file transfer
- delays between source-file requests
- arbitrary daily byte quotas

Resource controls should constrain **expensive preparation/concurrency**, not the transfer rate
of already-authorized static/source data.

### 3.3 Shared-hosting compatibility remains mandatory

The application remains a plain PHP 8.1+ application suitable for ordinary shared hosting.

Do not introduce:

- Composer dependency requirements
- npm runtime dependencies
- Redis
- Memcached
- message brokers
- background daemons
- worker services
- systemd services
- external queue services
- mandatory new PHP extensions
- mandatory CDN/proxy products

Filesystem locks, short-lived files, existing database facilities, and ordinary PHP crypto
functions are acceptable.

### 3.4 Every stage must be deployable independently

After **every individual stage**:

- public gallery pages must still load normally;
- physical gallery downloading must still work;
- Smart Gallery downloading must still work where enabled;
- existing authenticated/admin workflows must remain functional;
- a deployment must not require the next stage to make the current stage usable;
- rollback must be possible by reverting only the files modified by that stage.

Do not make a stage whose intermediate state intentionally breaks downloads pending the next
stage.

### 3.5 Security checks must remain server-side

HTML attributes, `robots.txt`, `nofollow`, JavaScript-only buttons, or hidden URLs are useful
crawler hygiene but are **not authorization boundaries**.

All actual access decisions must continue to be performed server-side.

### 3.6 Preserve comments and docblocks

Do not delete existing comments, docstrings, or file headers while implementing this plan.
Update documentation and comments where behavior changes.

## 4. Target architecture

The desired steady-state physical-gallery flow is:

```text
PUBLIC GALLERY PAGE
        |
        | explicit user download action
        v
DOWNLOAD START / CAPABILITY HANDSHAKE
        |
        | cheap authorization + expiry + scope
        v
SIGNED SHORT-LIVED DOWNLOAD CAPABILITY
        |
        v
DOWNLOAD MANIFEST
        |
        | bounded metadata work, preferably revision-cached
        v
BROWSER DOWNLOADER
        |
        +--> authorized source file
        +--> authorized source file
        +--> authorized source file
        |
        v
BROWSER-SIDE ZIP ASSEMBLY
```

The legacy/no-JavaScript flow should ultimately be:

```text
PUBLIC GALLERY PAGE
        |
        | explicit form submission, NOT crawlable GET navigation
        v
LEGACY DOWNLOAD START
        |
        | capability + authorization + hard limits
        v
SINGLE-FLIGHT BUILD KEY
        |
        +--> cached completed artifact -> serve immediately
        |
        +--> existing build -> reuse / wait briefly / retry response
        |
        +--> no build -> acquire bounded preparation slot
                          |
                          v
                        build once
                          |
                          v
                    immutable cached artifact
                          |
                          v
                         serve
```

The Smart Gallery flow should receive equivalent protections where technically applicable,
while respecting that its result set is dynamic and may require a result/revision fingerprint
rather than a physical folder revision.

# STAGE 1: Observability, incident diagnostics, and passive crawler hygiene

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.

## Goal

Improve visibility and reduce accidental crawling **without changing the existing download
contract**. This is intentionally low risk and provides evidence needed to evaluate later stages.

## Required implementation

### 1.1 Enrich legacy failure logging

Update failure logging in `app/controllers/downloads.php` so that
`gallery.download_legacy_failed` records enough context to identify where and why a failure
occurred.

At minimum record:

- gallery ID;
- exception class;
- sanitized exception message;
- request method;
- route;
- request ID if the application already exposes one;
- download mode = `legacy`;
- a stable failure stage/reason when the code can determine it;
- User-Agent, bounded to a safe maximum length;
- Referer, bounded to a safe maximum length;
- remote-address context using the project's existing privacy/security conventions, if such a
  helper already exists.

Do not dump stack traces, secrets, filesystem paths, cookies, tokens, or arbitrary request
headers into the admin log.

Apply equivalent useful diagnostics to Smart Gallery legacy ZIP failures.

If service-level ZIP code currently turns failures into generic exceptions, add narrow internal
reason reporting where this can be done safely without changing public error messages.

### 1.2 Add crawler hints to existing public download anchors

While the legacy anchors still exist, add appropriate crawler-hygiene attributes such as
`rel="nofollow"` and, where appropriate, `download`/semantic attributes that do not break the
current JavaScript handler or no-JavaScript fallback.

Do not rely on these attributes for security.

### 1.3 Explicit search-engine exclusion for download endpoints

Review the current SEO request guard and any generated robots behavior. Add or document explicit
non-indexing treatment for download endpoints where it fits the existing architecture.

Responses from download initialization/manifest routes should not become indexable content.
Use standards-compatible headers such as `X-Robots-Tag: noindex, nofollow` where appropriate.

Do not accidentally add `noindex` to normal gallery pages.

### 1.4 Preserve current functionality

At the end of this stage:

- the current `<a href="...download_gallery...">` fallback still works;
- the current progressive JavaScript downloader still works unchanged from the visitor's
  perspective;
- Smart Gallery downloading still works;
- no new token is required yet.

## Tests for Stage 1

Add/extend automated tests where the repository test structure allows it, and perform manual
checks:

1. Normal JavaScript gallery download still opens the progressive dialog and downloads a ZIP.
2. Direct navigation to the legacy URL still performs the current bounded fallback.
3. Smart Gallery equivalent still works.
4. Failure logging contains the new diagnostic fields but no sensitive payloads.
5. Download responses are non-indexable while gallery pages remain indexable as before.
6. Existing test suite and PHP syntax checks pass on PHP 8.1+.

## Stage 1 rollback safety

Purely diagnostic/passive changes. Reverting this stage must restore the previous behavior
without data migration.

# STAGE 2: Introduce stateless signed download capabilities in parallel

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.
>
> Before this stage, operational download/browser-upload numeric limits were centralized in `app/configuration_defaults.php` and are consumed through `cms_runtime_limit()`. Protocol versions, enum names, and format hard limits remain module-local.

## Goal

Add a cheap capability mechanism **without requiring it yet**. Existing routes remain fully
functional while the new path is exercised and tested in production.

This stage deliberately avoids a hard cutover.

## Required implementation

### 2.1 Add a small download-capability service

Create a focused service rather than embedding crypto/token parsing throughout controllers.
The service should support physical galleries and, if cleanly possible, Smart Galleries.

A capability should encode only the minimum required claims, for example:

- version;
- resource type (`gallery` / `smart_gallery`);
- resource ID;
- scope (`manifest`, `source`, `legacy` or a deliberately designed combined scope);
- issued-at time;
- expiry time;
- random nonce when useful.

Sign the payload with HMAC-SHA-256 or an equivalently appropriate built-in primitive using a
server-side secret.

Requirements:

- use `hash_hmac()` and `hash_equals()` or existing project crypto helpers;
- no database row is required merely to validate a normal capability;
- validation must reject tampered tokens, expired tokens, wrong resource IDs, wrong resource
  type, and wrong scope;
- do not put filesystem paths, gallery passwords, share secrets, or private metadata in the
  token;
- token lifetime should be short enough to limit replay exposure but long enough for large
  legitimate downloads. Choose and document a concrete default based on the current client
  workflow;
- support key/format versioning so a later secret/format migration is possible;
- cap token length and reject malformed input before expensive processing.

### 2.2 Secret management

Integrate with the project's existing configuration conventions.

Preferred order:

1. reuse an existing application secret if it is explicitly intended for HMAC derivation;
2. otherwise add a dedicated configurable download-capability secret with safe install/update
   behavior;
3. if automatic derivation is used, document exactly which stable server secret is the root.

Do not hardcode a shared secret into the repository.

Do not make existing installations fail after update because a new configuration value is
missing. Provide backward-compatible initialization/derivation behavior.

### 2.3 Add a cheap `download start` endpoint

Add a public initialization endpoint for physical galleries and the Smart Gallery equivalent if
appropriate.

The endpoint performs only cheap work:

1. parse bounded input;
2. locate resource;
3. run existing visitor authorization;
4. verify downloading is enabled;
5. issue a short-lived signed capability;
6. return JSON containing the capability and next endpoint URL(s).

It must **not**:

- build a ZIP;
- traverse/read image payloads;
- hash source image contents;
- recursively walk the filesystem;
- create one database session row per download unless the existing architecture makes that
  unavoidable.

A failed initialization must also be cheap.

### 2.4 Compatibility mode

During Stage 2, manifests and file endpoints must still accept the old tokenless calls used by
the current frontend.

The new capability-aware path should be testable explicitly, but not mandatory.

Add a temporary internal compatibility switch/helper if useful, but do not expose confusing
admin UI solely for this transition unless required.

## Tests for Stage 2

Test at minimum:

- valid token issuance for a public downloadable gallery;
- rejection for inaccessible/private/nonexistent galleries;
- signature tampering;
- expiry;
- wrong gallery ID;
- wrong resource type;
- wrong scope;
- malformed/oversized token;
- Smart Gallery behavior where implemented;
- old tokenless progressive download still works;
- old direct legacy download still works.

## Stage 2 rollback safety

No database migration should be required just to revert this stage. Existing endpoints remain
backward compatible throughout this stage.

# STAGE 3: Move the progressive browser downloader onto the capability flow

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.
>
> The normal browser path now performs a same-origin POST to `download_*_start`, carries the
> progressive capability in `X-PHP-Gallery-Download-Capability`, and requires that capability on
> progressive manifest/source routes. Query capability transport remains accepted only as a
> bounded transition path. The default progressive capability lifetime is six hours from the
> explicit start handshake, and a rejected/expired capability causes the browser to discard any
> partial output and reinitialize on Retry. Legacy server ZIP routes remain tokenless-compatible.

## Goal

Make the normal JavaScript download workflow use the new explicit handshake and signed
capability while leaving the legacy fallback untouched for compatibility.

After this stage, ordinary modern-browser downloads no longer rely on a publicly reusable
manifest/file URL alone.

## Required implementation

### 3.1 Change the frontend initialization sequence

Update `public/assets/gallery-modules/gallery-download.js` and the rendered download metadata so
the normal flow becomes:

```text
click Download
  -> POST/fetch download-start
  -> receive capability + manifest URL
  -> fetch manifest with capability
  -> fetch each source URL with capability/derived authorization
  -> assemble ZIP in browser
```

Keep the existing user-facing progress dialog and cancellation behavior.

Do not add extra confirmation clicks.

### 3.2 Capability transport

Choose one consistent transport that works on the current shared-hosting stack.

Possible acceptable patterns:

- bounded query parameter on manifest/source URLs;
- `Authorization` header if routing/caching constraints make this reliable;
- another existing same-origin mechanism.

The design must account for:

- access logs potentially recording query strings;
- Referer leakage;
- browser retries;
- parallel source fetches;
- token expiry during large downloads.

If query parameters are used, set an appropriate Referrer Policy on responses/pages so the
capability is not leaked to unrelated origins.

### 3.3 Token lifetime during long downloads

A token that expires halfway through a multi-gigabyte gallery would damage UX.

Implement one of these explicitly documented approaches:

- sufficiently long short-lived capability measured from initialization;
- separate manifest capability that returns source capabilities with suitable expiry;
- cheap refresh endpoint that can renew an active same-resource capability.

Do not create an unbounded permanent bearer URL.

### 3.4 Preserve legacy path

`download_gallery` and `download_smart_gallery` must still operate exactly as before at the end
of Stage 3. They remain the no-JavaScript fallback for now.

### 3.5 Authorization parity

The capability must never grant access that the existing visitor authorization would deny.

In particular preserve:

- root gallery access rules;
- child-gallery visibility filtering;
- image visibility filtering;
- Smart Gallery publication/download settings;
- share/token behavior already supported by the product.

## Tests for Stage 3

1. Normal physical gallery browser ZIP download succeeds.
2. Large galleries continue to use browser-side assembly.
3. Cancellation still aborts network work.
4. Source file requested without required capability is rejected in capability-enforced mode.
5. Token for gallery A cannot fetch gallery B.
6. Image outside the authorized subtree cannot be fetched.
7. Expired capability produces a controlled retry/restart UX, not a broken partial ZIP.
8. Existing direct legacy URL still works.
9. Smart Gallery download still works.
10. Existing ZIP/ZIP64 JavaScript tests remain green.

## Stage 3 rollback safety

Because legacy remains intact and server endpoints retain a controlled compatibility path during
this transition, reverting frontend/server changes restores the Stage 2 behavior.

# STAGE 4: Remove crawlable GET-triggered legacy ZIP generation

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.
>
> Public gallery and Smart Gallery download controls are now explicit POST forms with resource-scoped `legacy` capabilities instead of crawlable legacy anchors. JavaScript progressively enhances the same submit button by intercepting it and starting the Stage 3 browser ZIP flow, while no-JavaScript or failed-JavaScript clients naturally submit the bounded legacy fallback. Historic legacy GET URLs render only a cheap confirmation form, and ZIP construction is POST-only with mandatory capability validation. Progressive `download_*_start` initialization is also POST-only and no longer mints legacy bearer URLs.

## Goal

Close the specific surface observed in the incident: a crawler following a public anchor must no
longer start server-side ZIP construction.

This is the behavioral cutover, but it must preserve a usable no-JavaScript fallback.

## Required implementation

### 4.1 Replace download anchors with explicit actions

For physical galleries and Smart Galleries, stop rendering the legacy server ZIP endpoint as the
ordinary crawlable anchor `href`.

Preferred normal-JavaScript rendering:

```html
<button type="button" ...>Download</button>
```

or an equivalent accessible control already consistent with the project UI.

The JavaScript handler starts Stage 3's capability workflow.

### 4.2 Preserve no-JavaScript download capability

Do **not** simply remove legacy downloading.

Provide a progressively enhanced fallback that requires explicit form submission rather than
crawler navigation. For example, inside a `<noscript>` block or equivalent accessible fallback:

```text
POST legacy-download-start
```

The form should contain only the minimum resource identifier and an anti-replay/signed form
capability appropriate for a public anonymous action.

A normal search crawler parsing links should not trigger it because there is no GET download URL
to follow.

Do not claim this form prevents a malicious scraper from submitting it. Its purpose is to remove
**accidental crawler execution** while the later stages make malicious execution inexpensive.

### 4.3 Legacy GET compatibility transition

Do not immediately turn historic/bookmarked GET URLs into expensive builds.

The old `GET download_gallery?id=...` route should become cheap. Choose a backward-compatible
response such as:

- a lightweight informational page with an explicit Download button/form;
- a redirect to the gallery page with a download intent marker that does not itself build;
- HTTP 405 only if compatibility analysis confirms this will not harm supported behavior.

Preferred outcome: old URLs still lead the visitor to a working download without performing a
ZIP build merely because the URL was fetched.

No GET request should invoke `build_gallery_zip()` or `build_smart_gallery_zip()` after this
stage.

### 4.4 Require deliberate legacy initiation

The actual legacy server ZIP operation should require:

- POST or another non-crawl navigation action;
- a valid short-lived capability scoped to the exact resource and legacy action;
- existing gallery authorization;
- existing hard file/byte limits.

CSRF semantics should be considered carefully. This is an anonymous public operation, so do not
misuse an admin-session CSRF token if that would require cookies/accounts. The signed capability
itself can provide request binding where designed correctly.

### 4.5 Keep public UX simple

A user with JavaScript:

- clicks Download once;
- sees the existing progress UI;
- downloads normally.

A user without JavaScript:

- sees a clear fallback Download control;
- submits it;
- receives a legacy ZIP only when within the legacy bounds.

No CAPTCHA, email, account, or arbitrary waiting screen.

## Tests for Stage 4

Critical regression tests:

1. Fetch a gallery HTML page with a non-JavaScript HTTP client. Verify there is no crawlable
   legacy ZIP GET URL that starts a build.
2. GET the historic `download_gallery?id=N` URL. Verify **no ZIP build is started**.
3. Normal JS physical gallery download succeeds.
4. Normal JS Smart Gallery download succeeds.
5. No-JS explicit physical gallery fallback succeeds for a small gallery.
6. No-JS explicit Smart Gallery fallback succeeds where supported.
7. Oversized legacy gallery still receives the bounded explanatory response.
8. Invalid/tampered legacy capability cannot start a build.
9. Private/inaccessible gallery cannot start a build.
10. Search-engine crawler fetching all page anchors cannot cause legacy ZIP preparation.

## Stage 4 rollback safety

Keep legacy building code present. This stage changes how it is entered, not yet how the ZIP is
built internally. Reverting this stage restores the previous anchor/GET behavior.

# STAGE 5: Single-flight deduplication and bounded legacy build admission

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.
>
> Physical and Smart Gallery legacy ZIP preparation now uses canonical content/result revisions, non-blocking per-build `flock()` single-flight locks, and a shared configurable filesystem slot pool with a default of two simultaneous expensive builds. Cache hits bypass admission, busy requests receive `503` plus `Retry-After`, and completed downloads are not bandwidth-throttled. Physical gallery publication now uses unique partial files plus atomic rename; Smart Gallery publication remains atomic and its dynamic result fingerprint is revalidated before publication. Persistent lock files are safe after process crashes because ownership is the kernel flock, not file contents.

## Goal

Make deliberate or malicious repeated legacy-start requests unable to create an unbounded number
of concurrent expensive ZIP builds.

This stage controls **preparation concurrency**, not download bandwidth.

## Required implementation

### 5.1 Define a canonical legacy build key

A build key must be based only on fields that change the resulting archive, for example:

```text
resource_type
resource_id
resource_revision/result_fingerprint
archive options that actually affect contents
```

Do **not** include:

- capability token;
- random nonce;
- client IP;
- User-Agent;
- irrelevant query string parameters;
- request ID.

Otherwise attackers could bypass deduplication by cache-busting.

### 5.2 Resource revision/fingerprint

For physical galleries, use a cheap existing revision/signature mechanism if one is already
canonical and reliable. The codebase currently contains gallery ZIP signature concepts that
should be reviewed before inventing another incompatible revision model.

The fingerprint must change when archive contents change, including relevant:

- image addition/removal;
- image replacement;
- filename/path change affecting ZIP entry names;
- gallery/subgallery structure change;
- visibility change that changes downloadable membership.

Do not hash every source payload on every request merely to compute the revision.

For Smart Galleries, define a bounded result fingerprint suitable for dynamic membership. If a
stable cheap fingerprint cannot be guaranteed, Smart Gallery legacy caching may use shorter TTL
and stronger single-flight locking rather than pretending the result is immutable.

### 5.3 Per-build single-flight lock

Before constructing a legacy ZIP:

1. compute canonical build key;
2. check completed artifact cache;
3. attempt to acquire an exclusive lock for that build key;
4. if another request already holds the lock, **do not start another build**.

Use shared-hosting-safe locking, preferably atomic filesystem creation/flock in a private cache or
temporary directory already protected from public execution/listing.

Handle stale locks safely after crashed PHP requests.

### 5.4 Global bounded build admission

Single-flight prevents duplicate builds of the same gallery, but an attacker could request many
different galleries. Add a global limit on simultaneous expensive legacy builds.

Implementation must be safe without Redis/daemon infrastructure.

Possible design:

- a small filesystem semaphore/slot directory;
- database-backed lease rows if the existing DB is clearly more reliable for atomic claims;
- another existing application lock primitive.

Requirements:

- choose a conservative configurable/default global concurrent-build count suitable for shared
  hosting;
- stale leases must expire/recover;
- do not block PHP workers indefinitely waiting for a slot;
- if capacity is unavailable, return a controlled retryable response such as `429` or `503`
  with `Retry-After`;
- frontend/no-JS response should explain that preparation capacity is temporarily busy;
- do not convert this into a bandwidth limit after the artifact exists.

### 5.5 Per-resource concurrency

Only one build for the same canonical build key should occur at once.

Multiple clients may download the completed same artifact concurrently.

### 5.6 Failure cleanup

On exceptions/fatal-path cleanup where possible:

- release owned build slots;
- release/remove owned lock state;
- never publish a partial artifact as complete;
- leave enough metadata to identify stale partials for maintenance;
- do not delete another request's valid lock/artifact.

Use atomic finalization, such as writing/building to a temporary name then renaming only after a
successful close/validation.

## Tests for Stage 5

Concurrency tests should verify:

1. 10 simultaneous requests for the same gallery result in exactly one build attempt.
2. Other requests reuse/wait/retry rather than build duplicates.
3. Requests for many different galleries never exceed the configured global build count.
4. Completed artifact downloads are not bandwidth-throttled by the build admission limit.
5. A crashed/stale lock recovers safely.
6. A failed build does not create a valid-looking cached artifact.
7. Query-string/capability variations do not create distinct build keys.
8. Different true gallery revisions do create distinct build keys.
9. Existing legacy file/byte caps remain enforced before expensive build work.

## Stage 5 rollback safety

If the new lock/admission service is removed, the Stage 4 explicit legacy initiation remains
functional using the previous bounded builder. No persistent schema dependency should make
rollback impossible; if a schema table is added, old code must tolerate its presence.

# STAGE 6: Immutable legacy artifact cache and safe maintenance

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.
>
> Legacy physical and Smart Gallery fallback ZIPs now publish into a private immutable `legacy-artifacts` subtree keyed by resource revision and canonical Stage 5 build key. Archive publication requires successful ZIP close, exact entry-count sanity, bounded metadata persistence, and atomic directory rename. Physical artifacts expire after 7 days; Smart Gallery result-fingerprint artifacts after 24 hours. Abandoned partials are eligible after 6 hours, inactive reservation/build coordination state after 24 hours, and cleanup uses build/serve `flock()` ownership so active work is skipped. New builds reserve against a 4 GiB managed-cache budget and preserve a 512 MiB filesystem free-space margin by default. Capacity refusal is logged distinctly and returned as HTTP 507. These deployment defaults remain centrally overridable through `runtime_limits`.

## Goal

Ensure repeated requests for unchanged downloadable content reuse an already completed server ZIP
rather than rebuilding it.

This makes deliberate repeated legacy requests much cheaper after the first permitted build.

## Required implementation

### 6.1 Private immutable artifact location

Store completed legacy artifacts under a private, non-executable, non-listable application cache
location using the canonical build key/revision.

Example logical layout only:

```text
cache/downloads/
  physical/
    <gallery-id>/
      <revision>/
        gallery.zip
        metadata.json
```

Do not expose actual filesystem paths in public URLs or logs.

If Apache can safely serve a completed authorized artifact directly using existing protected-file
routing, evaluate that optimization, but do not weaken authorization merely to bypass PHP.

### 6.2 Atomic publication

A completed artifact becomes reusable only after:

- ZIP creation succeeded;
- ZIP close succeeded;
- expected file exists;
- nonzero/expected sanity checks pass;
- metadata is written successfully.

Publish via atomic rename where the hosting filesystem supports it.

### 6.3 Metadata

Store enough bounded metadata to determine:

- build key;
- resource ID/type;
- resource revision;
- creation time;
- archive size;
- optional expected file count;
- cache format version.

Do not store bearer capabilities or visitor identifiers in artifact metadata.

### 6.4 Reuse behavior

Legacy start sequence becomes:

```text
authorize
 -> validate legacy limits / revision
 -> completed artifact exists?
      YES: serve it
      NO: single-flight/admission -> build once -> publish -> serve
```

Capability/token differences must not create separate artifacts.

### 6.5 Cache retention and maintenance

Integrate cleanup into the existing maintenance architecture rather than inventing a daemon.

Cleanup should remove:

- expired old revisions;
- abandoned partial build files;
- stale metadata;
- orphaned locks/leases after safe age checks.

It must **not** remove an artifact currently being built or served merely because another
maintenance request runs concurrently.

Choose documented retention defaults. Prefer size/age-aware cleanup if the current maintenance
framework supports it cleanly.

### 6.6 Disk-exhaustion protection

A cache can itself become a DoS vector.

Before starting a new cache build, enforce bounded storage policy using available safe checks.
At minimum:

- refuse new builds when the configured cache budget/free-space safety margin would be violated;
- never delete arbitrary application/gallery files to make space;
- clean only managed download-cache artifacts;
- log capacity refusal as a distinct operational event.

## Tests for Stage 6

1. First legacy request builds once.
2. Second request for the unchanged gallery performs no ZIP rebuild.
3. Gallery mutation changes revision and creates a new artifact.
4. Old artifact remains isolated from the new revision until maintenance removes it.
5. Partial files are never served.
6. Maintenance removes only eligible managed artifacts.
7. Disk-capacity refusal produces a controlled response and no broken ZIP.
8. Parallel serving and cleanup cannot delete an in-use/being-built artifact incorrectly.
9. Smart Gallery caching follows its documented fingerprint/TTL semantics.

## Stage 6 rollback safety

Stage 5 continues to provide bounded single-flight builds even if artifact reuse is disabled.

# STAGE 7: Progressive manifest cost hardening, source-serving review, and final legacy demotion

> **Implementation status:** Implemented in the current working tree on 2026-09-03. Deployment/manual production verification remains pending.
>
> Progressive physical and Smart Gallery manifests now derive a content-only revision after current capability and visitor authorization, then reuse private normalized metadata that contains only ZIP names, source image IDs, stable source versions, and byte sizes. Capability strings, visitor identity, request IDs, hosts, and unrelated query parameters are never part of cache identity or cache payloads. Cache misses retain the previous source existence/containment/size checks, while cache hits avoid repeating that per-file filesystem work. Physical metadata defaults to 24-hour retention, Smart Gallery metadata to 15 minutes, and bounded maintenance removes expired/corrupt entries. Manifest requests expose credential-free `Server-Timing` plus `X-PHP-Gallery-Manifest-Cache`, and active Admin test runs capture SQL-count, row-count, filesystem-check, elapsed-time, and memory diagnostics. Progressive manifest/source controllers now reject malformed methods and parameters before capability, DB, or filesystem work. Source delivery intentionally remains authorized PHP `readfile()` streaming because no portable protected internal-redirect facility can be assumed on supported shared hosting. Generated source URLs carry non-secret revision/size snapshots so a verified filesystem-size mismatch can invalidate only the exact stale manifest entry, and both Stage 7 snapshot parameters (`mr`, `s`) are explicitly accepted by the pre-dispatch SEO request guard. SEO guard rejection logs retain the request path but redact all query-string values, so compatibility query capabilities/share tokens cannot be copied into Admin security logs. The legacy builder independently rechecks actual source bytes before ZIP creation so cached metadata cannot weaken the hard legacy byte cap.

## Goal

Close secondary resource-amplification opportunities after the main legacy problem is fixed.
This stage hardens the normal progressive path so an attacker cannot simply shift abuse from ZIP
creation to repeated manifest generation or expensive PHP-mediated file preparation.

## Required implementation

### 7.1 Profile actual manifest cost first

Before adding caching, measure the current physical and Smart Gallery manifest operations:

- SQL query count;
- row counts;
- filesystem `stat`/`filesize` calls;
- elapsed time for small, medium, and very large galleries;
- memory use where existing diagnostics support it.

Do not optimize based on assumptions alone.

### 7.2 Revision-keyed manifest caching where justified

If profiling shows meaningful cost, cache normalized manifest metadata by resource revision.

A manifest cache must not weaken visitor authorization. Separate:

- reusable resource metadata;
- visitor/share authorization;
- short-lived capability URLs.

Do **not** cache bearer capability strings into a global reusable manifest file.

A safe conceptual model is:

```text
cached immutable manifest DATA
        +
current request authorization/capability
        =
response manifest with authorized URLs
```

For Smart Galleries, use bounded TTL/result fingerprinting appropriate to their dynamic query
semantics.

### 7.3 Prevent manifest cache-busting

Cache identity must ignore irrelevant URL/query parameters and client-specific values.
It should be derived only from content-affecting resource state.

### 7.4 Review source-file delivery cost

The current progressive source endpoint performs authorization and then streams with `readfile()`.
Review whether the hosting/application architecture provides a safe way to reduce long-lived PHP
worker occupancy while preserving authorization, for example an existing internal redirect or
protected static-file mechanism.

This optimization is optional unless supported safely by the actual hosting stack.

Do **not**:

- make original source files globally public merely to avoid PHP;
- expose predictable filesystem paths;
- assume Apache modules unavailable on ordinary hosting;
- require a new extension/server module.

If no safe portable mechanism exists, keep the existing authorized PHP streaming path and
concentrate on cheap authorization and bounded initialization.

### 7.5 Cheap rejection order

Review all download controllers so inexpensive validation occurs before expensive work.
Typical order:

1. method/parameter length/type validation;
2. capability signature/expiry/scope validation where applicable;
3. resource lookup;
4. visitor/resource authorization;
5. revision resolution;
6. cache lookup;
7. bounded manifest/build work;
8. payload transfer.

Avoid filesystem traversal or ZIP construction before authorization.

### 7.6 Final legacy status

After production evidence confirms the progressive flow is stable:

- keep the legacy path only as an explicit bounded compatibility feature;
- ensure no public normal page exposes a crawlable build-triggering URL;
- ensure GET requests never create ZIPs;
- keep hard size/file caps;
- keep capability requirement;
- keep single-flight/global admission;
- keep artifact reuse and maintenance;
- document the legacy path as intentionally limited and secondary.

Do not remove no-JavaScript support unless a separate product decision explicitly requests it.

### 7.7 Final documentation

Update at minimum the appropriate existing documentation files, likely including:

- `ARCHITECTURE.md`
- `CODEMAP.md`
- `TESTING.md`
- relevant security/viewer documentation under `docs/`
- configuration documentation if new settings/secrets exist

Document:

- threat model;
- capability design and expiry semantics;
- GET safety invariant;
- progressive flow;
- legacy flow;
- build concurrency limits;
- cache lifecycle;
- operational log events;
- maintenance behavior;
- rollback/recovery notes.

Do not edit `PATCH_NOTES.md` as part of this TEMP-plan implementation unless separately
requested for release preparation.

## 5. Cross-stage implementation rules

These apply to every stage.

### 5.1 Never use IP address as the primary identity/security boundary

IP data may be a supporting abuse/diagnostic signal, but do not assume one IP equals one visitor.
Legitimate users can share NAT, CGNAT, VPN, corporate proxy, or secure web gateway egress.

Do not build the primary download authorization model around IP pinning.

### 5.2 Rate-limit expensive work, not ordinary data transfer

Acceptable controls include:

- max concurrent new legacy builds;
- one build per canonical build key;
- bounded initialization request rate only if later evidence proves necessary;
- retryable admission control when all build slots are occupied;
- disk cache budget.

Avoid arbitrary restrictions such as:

- three downloads per hour per visitor;
- one gallery per day;
- fixed MB/s transfer caps.

### 5.3 Avoid request amplification in logging

An attacker may generate thousands of invalid requests. Logging must not become the next DoS
vector.

Use the existing admin-log grouping/deduplication mechanisms where available. Consider bounded
sampling/grouping for repeated capability failures rather than writing enormous unique payloads.
Never log full bearer tokens.

### 5.4 Use constant-time signature comparison

All cryptographic MAC/signature comparisons must use `hash_equals()` or the project's equivalent.

### 5.5 Bound attacker-controlled input before parsing

Apply strict maximum lengths and expected character/encoding formats to:

- capability tokens;
- IDs;
- version parameters;
- filenames returned in headers;
- query parameters used by download routes.

### 5.6 No path trust from token/client

Capabilities should reference logical IDs/scopes, never client-supplied absolute paths.
Continue resolving filesystem paths server-side and verifying containment with existing helpers
such as `path_inside()`.

### 5.7 Preserve source-change detection

The progressive downloader currently uses per-source version information and rejects a source
that changed after manifest creation. Preserve or strengthen this behavior.

### 5.8 Cache authorization separately from cached content identity

A cached ZIP/manifest represents resource content, not a visitor identity.

Always authorize the current request before serving protected cached content.

### 5.9 Use atomic filesystem operations

For locks, temporary artifacts, metadata, and publication, prefer atomic primitives supported by
the actual shared-hosting filesystem. Avoid check-then-create races.

### 5.10 No silent failure fallback into expensive behavior

If the capability, cache, lock, or admission subsystem fails, do **not** silently fall back to
unbounded ZIP creation.

Fail safely with a controlled retry/error response and log the operational reason.

## 7. Required security invariants after final stage

The implementation is complete only when all of these are true.

### Public page / crawler invariants

- Fetching a public gallery page does not create download artifacts.
- Following every ordinary anchor on that page does not trigger server ZIP creation.
- `GET download_gallery` never builds a ZIP.
- `GET download_smart_gallery` never builds a ZIP.

### Capability invariants

- Tampered/expired/wrong-scope capabilities are rejected cheaply.
- A capability for one gallery cannot access another gallery.
- Capabilities do not contain filesystem paths or secrets.
- Full capability values are not written to logs.

### Authorization invariants

- Existing visitor/gallery/share authorization remains authoritative.
- Private/hidden/non-visible sources cannot be downloaded through alternate IDs.
- Smart Gallery download settings remain enforced.

### Resource invariants

- One canonical legacy build key can have at most one active build.
- Total simultaneous legacy builds are globally bounded.
- Repeated requests for an unchanged completed artifact do not rebuild it.
- Irrelevant query/token changes do not bypass build/cache deduplication.
- Failed/partial builds are never served as completed ZIPs.
- Managed cache growth is bounded/maintained.

### UX invariants

- A normal modern-browser visitor clicks Download once and receives the existing progressive UX.
- No CAPTCHA/email/account is introduced.
- No intentional bandwidth throttling is introduced.
- A no-JavaScript visitor still has a functional bounded fallback.

### Compatibility invariants

- PHP 8.1+ remains supported.
- Shared-hosting deployment remains supported.
- No new mandatory service or daemon exists.
- Updater/install behavior handles any new config/storage requirements safely.
