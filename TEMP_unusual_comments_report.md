Removing or rewriting them would create inconsistency rather than materially improve human authorship signals.

## Findings

### 1. Light-bulb icon in an Admin formatting-help control — review recommended

Location: `app/controllers/admin_galleries_discovery.php:552`

The formatting-hints disclosure summary contains a visible `💡` before the translated label. This is a normal UX metaphor, not proof of AI generation, but it is the strongest match for the requested “stupid icons / smiley faces” concern because it is an emoji embedded directly in application markup.

Suggested solution: replace it with a neutral CSS/icon-system symbol, plain text, or no icon. If retaining an icon, use an existing project icon convention and keep it decorative (`aria-hidden`). Update the corresponding view/part file if the delegated renderer is the active path, and update any focused markup contract that asserts the summary.

Risk: low. This is cosmetic, but changing it may require checking the Admin formatting-help layout and accessibility output.

### 2. Globe and country-flag glyphs in the OpenAI language catalog — legitimate, not suspicious

Location: `app/services/openai_text_assist.php:596` and adjacent language entries.

The language selector uses a globe and country flags. These are functional language indicators, not comments or author-facing prose. They do not resemble a model signature. Keep them unless the product wants to avoid emoji rendering differences across operating systems; in that case use text labels or a controlled icon asset.

### 3. Smiley in a test fixture — legitimate test data, not user-facing

Location: `tests/viewer_account_lifecycle_phase07_test.php:173`

The test repeats `🙂` to validate Unicode character and byte limits. It is deliberately exercising multibyte input and should remain. It is not documentation, a docstring, or production UI.

### 4. Checkmarks, crosses, hearts, and checkbox symbols — functional UI symbols

Locations include `app/views/admin_upload_settings.php`, `app/controllers/public_gallery_page.php`, `app/controllers/public_gallery_controls.php`, and `public/assets/gallery-modules/viewer-favourites.js`.

These symbols communicate support/status, selection, and favourite state. They are not suspicious comments or model boilerplate. Review only if the project has a broader policy against Unicode UI glyphs; that would be a design-system decision, not an AI-authorship cleanup.

### 5. Legitimate AI/OpenAI wording — feature terminology, not authorship leakage

Occurrences such as `OpenAI`, `AI-generated text`, `AI worker`, and model catalog names appear in feature code, settings, tests, documentation, and release notes. They describe shipped functionality and should not be removed. They do not claim that the repository itself was generated by an AI model.

### 6. Standardized comments and defensive wording — not suspicious

There are many comments using phrases such as “This module…”, “This avoids…”, “This is intentionally…”, “deliberately”, “fallback”, and “defense-in-depth”. They consistently explain module boundaries, security behavior, compatibility paths, and lifecycle constraints. Their repetition reflects a documentation convention and architecture-heavy codebase. I found no isolated conversational comment that reads like a model’s self-reference or generation note.

The frequent `Notes:` header line is likewise a repository-wide file template, not an unusual one-off comment.
